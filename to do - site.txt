AI implementation
Simple approach: Add a small “Ask AI” input in your UI (e.g., “Select for me a 2-day timetable”).
Send that text to a backend endpoint (not directly from browser, so API key stays private).
Use an LLM to return strict JSON like:
{
  "intent": "build_timetable",
  "max_days": 2,
  "preferences": []
}
In your existing app logic, run a deterministic timetable selector using your current subject/timetable data.
Show 1-3 valid timetable options and let user click “Apply”.
Why this is easiest

AI handles natural language.
Your codebase keeps control of business rules/prereqs.
More reliable than letting AI “pick” subjects on its own.
If you want, I can next give you a minimal backend + prompt/schema design tailored to your current script.js flow without changing anything yet.

Short answer:

Do you need a paid API key?
Yes, typically yes. API usage is billed separately from ChatGPT subscriptions. So even if someone has ChatGPT Plus/Business/Edu, API costs are a different billing stream.
(There may be limited trial/contract credit situations, but production use is usually paid.)

How it works for colleagues/students
Best setup: one backend-owned API key (your org), not user keys in browsers.
Your app users (staff/students) use the UI normally; your server calls the API and enforces:

per-user limits
role rules (staff vs student)
logging/audit
spend caps/rate limits
Should you predefine JSON possibilities?
Yes. Use a small fixed schema (intents + constrained fields), and let AI map free text into that schema.
Also give users clickable suggested options (“2-day timetable”, “avoid Friday”, etc.) that populate the same JSON structure.
So: not endless custom JSON per user, but one controlled schema for everyone.

Disclaimer: Create a tooltip popup that addresses this concern: "As more companies turn to generative AI to communicate with their customers, experts say a generic disclaimer like 'AI makes mistakes' isn’t good enough." Add that ultimately it's the student's responsibility to choose their own timetable.  AI can help you and enrolment officers will double-check your selections and try to assist. given how this site is built now, the key decision is not “DB or Excel” in isolation, but where the single source of truth lives.

Right now the app is a large static website that already knows how to read Source.xlsx and Triage.xlsx. That makes an Excel-based replacement easier in the short term. But if you want data to be edited reliably from the website, opened independently, and stay consistent over time, a database-backed model is the stronger design.

My recommendation is:

Make a database table the source of truth for triage data.
Let the website load and edit that table through a small backend/API.
Add Excel import/export so staff can still open the data independently in Excel when needed.

Best long-term: Database + API
Store one row per student triage record.
Include fields like student ID, friendly name, handled by, status, altered status, comments, in-strata, SharePoint link, modified by, modified at.
Website reads and updates via API.
Add “Export to Excel” and optionally “Import from Excel”.
Best if multiple staff use it or data quality matters.


Middle ground: Local database file
Use something like SQLite as a single file that can be opened independently and also used by the site through a small local helper app.
Better structure than Excel, simpler than a server DB.
Good if this is mostly one user on one machine, or a shared file with very limited simultaneous editing.
Still not ideal for multi-user concurrent staff access over OneDrive/SharePoint.

A practical rollout path would be:

Define the triage columns and rules clearly.
Build a DB schema that mirrors the current Triage workbook fields.
Import the current Triage.xlsx once.
Make the site read from the DB instead of parsing the workbook.
Add edit/save from the site.
Add export to .xlsx for offline/open-independent use.
If you want, I can next help you choose between three concrete implementations for your environment:


For your current Microsoft/OneDrive/SharePoint-heavy setup, a SharePoint List is probably the most pragmatic first DB-like option. It is independently openable, editable outside the site, and easier to integrate operationally than standing up a full custom database server.
